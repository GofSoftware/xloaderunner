## Commands

- `npm start` — dev server (`ng serve`, default port 4200, live reload on file changes)
- `npm run build` — production build to `dist/lr`
- `npm run watch` — dev-mode build in watch mode
- `npm test` — unit tests (`ng test`, Vitest runner in a jsdom environment)
  - Single file: `npm test -- --include src/app/engine/screen/screen-buffer.spec.ts`
  - Filter by suite/test name: `npm test -- --filter "ScreenBuffer"`
- `npx ng generate component <name>` / `npx ng generate service <name>` — scaffold new pieces; this repo generates first, then hand-edits, so prefer this over writing boilerplate by hand.

No lint script/config is set up in this repo.

Formatting: Prettier (`.prettierrc`) — 140-char print width, single quotes, Angular parser for `.html`.

When reading, searching, or editing files in this repo, use the dedicated Read/Edit/Write/Grep/Glob tools rather than shell commands (`sed`, `awk`, `cat`, `find`, heredocs) — including for a repetitive edit applied across several files one at a time.

## Project layout

`src/app/` is split by what depends on Angular and what doesn't:

- **`src/app/ui/`** — all Angular-bound code (components, anything using `@Component`/signals tied to the DOM). New components go under `src/app/ui/components/<name>/`. This is the *only* place Angular-specific code should live.
- **`src/app/engine/`** — framework-agnostic game code: the `Engine` game loop, the `GameObject`/`Script` component system, math primitives, and the screen/buffer primitives the engine drives. Nothing in here knows Angular exists — it's plain TypeScript classes, no DI, no `@Component`/`@Service`. Subfolders:
  - `engine/game-object/` — `GameObject` and the `Script` base class.
  - `engine/math/` — `Vector2`.
  - `engine/screen/` — `ScreenBuffer`, `ScreenHelper`, `screen.constants.ts`.
  - `engine/scripts/` — concrete `Script` subclasses (renderers, behaviors).
  - Naming convention in this layer differs from `ui/`: interfaces are prefixed `I` (`IGameObject`, `IScript`, `IVector2`, `IEngineState`), and classes with a static `create()` factory keep their constructor `private` (`GameObject`, `Vector2`, `ScreenBuffer`).
- **`src/app/data/`** — plain data: pixel-art constants (`glyphs.ts`, `sprites.ts`). No logic, no Angular, no engine dependencies — just literal `number[][]` arrays.

## Architecture

This is an Angular 22 app, **zoneless** (no `zone.js`) and **moduleless** (standalone components only, no `NgModule`s anywhere). File/class naming follows the 2025 Angular style guide: no type suffixes (`app.ts` exports `App`, `header.ts` exports `Header`). Angular services (where still used, e.g. none currently in the engine layer) use the newer `@Service()` decorator rather than `@Injectable({ providedIn: 'root' })`.

The app renders a tiny fixed-resolution pixel "screen" (256×192, a ZX-Spectrum-like resolution) that auto-scales to fill the browser window width while preserving aspect ratio. The engine and UI layers are deliberately decoupled — the engine drives frames and owns pixel data; the UI layer only knows how to paint a buffer snapshot to canvas.

### Engine and the GameObject/Script component system

- **`Engine`** (`src/app/engine/engine.ts`) is a plain-TypeScript singleton (private constructor, lazily created via the static `Engine.instance` getter) and implements `IEngineState` (see below). It owns a `ScreenBuffer` and a `gameObjects: GameObject[]` list, and drives the game loop:
  - `start(game: IGame)` records `previousFrameTime`, sets `started = true`, stores `game` (exposed back to scripts via the `game` getter), awaits `game.start(this)` to let the game build its scene's `GameObject`s, and then calls `render()` directly to kick off the loop.
  - `stop()` clears `started` (so the render loop's next `setTimeout` tick is a no-op) and calls `.destroy()` on every game object — use this to shut the engine down entirely (e.g. between tests).
  - `reset()` also destroys and untracks every game object, but leaves `started` alone and additionally clears the keyboard's held/pressed state (`this.keyboard.reset()`) — use this to clear the scene between levels/screens *without* stopping the render loop, so the next frame keeps ticking and can safely add a fresh set of game objects (see `XLodeRunnerGame.startLevel()` below).
  - `registerAfterUpdate(fn)` queues a one-shot callback that runs at the tail of the *current* `render()` call — after every game object's `.update()` for this frame, and after the next frame is already scheduled via `setTimeout`, but before that next frame actually fires. Use this from inside a script's `update()` for any action that would otherwise destroy game objects mid-frame (like a full `reset()`) — doing that synchronously would corrupt `render()`'s `[...this.gameObjects].forEach(...)` snapshot for every object not yet updated this frame, the same class of bug documented below for two scripts reacting to one keypress. `LivesScript.loseLife()` is the current user: it defers a level restart this way instead of triggering it immediately.
  - `setRender(uiRender)` lets any UI layer register a callback of shape `(buffer: Readonly<number[][]>) => void` — this is the *only* connection between Engine and the UI; Engine never imports anything Angular.
  - A private `render()` computes `deltaTime` (in seconds), calls `.update()` on every game object (which is what actually mutates `ScreenBuffer` — see below), invokes the registered `uiRender` callback with the buffer, and reschedules itself via `setTimeout(() => this.render(), FRAME_RATE)` (`FRAME_RATE` is currently `0`, i.e. "as fast as the timer allows" — a placeholder, not a real frame-rate limiter yet).
- **`IEngineState`** (`src/app/engine/i-engine-state.ts`) is the interface `Engine` implements and the only thing a `GameObject`/`Script` sees of it — the screen/keyboard/audio handles, frame timing, the current `game: IGame`, and the `addGameObject`/`removeGameObject`/`getGameObjectByName`/`getGameObjectsByName`/`renameGameObject` registry methods. This is how engine-driven code reaches everything Engine owns without depending on the `Engine` class itself. `getGameObjectByName` returns only the first-added match; `getGameObjectsByName` returns every tracked `GameObject` sharing that name, in add order (e.g. every `Enemy`, since levels can place more than one under the same name).
- **`IGame`** (`src/app/engine/i-game.ts`) is the engine's entry point into game-specific code — the only thing `Engine.start()` takes: `start(engineState): Promise<void>` (build the initial scene) and `onMoseMove(x, y): void` (forwarded from `Screen`'s mousemove handler). It's the one piece of the game/engine split allowed to live in `engine/` despite being game-facing, precisely because `Engine` needs to call it. `game-x-loade-runner/x-lode-runner-game.ts`'s `XLodeRunnerGame` is the concrete `IGame` — it owns a list of level factories and switches between them (see below).
- **`ILevel`** (`src/app/game-x-loade-runner/i-level.ts`) is game-specific (it references `Tile`), so it lives under `game-x-loade-runner/`, not `engine/`: `{ engineState, map: TileElement[][], initialize(): Promise<GameObject[]> }`. `initialize()` builds and returns the level's `GameObject`s without adding them to the engine itself — `XLodeRunnerGame.startLevel()` does that, after calling `engineState.reset()` to clear whatever the previous screen left behind, and after also adding shared HUD objects common to every level.
- **`game-x-loade-runner/data/level/`** holds one file per `ILevel`: `x-lode-runner-level.ts` exports the abstract `XLodeRunnerLevel` base class (shared tile-map/player/enemy setup logic), `x-lode-runner-level-1.ts` is the concrete playable level (its `TileElement[][]` map literal plus `XLodeRunnerLevel1 extends XLodeRunnerLevel`), and `start-menu-level.ts`'s `StartMenuLevel`/`game-over-level.ts`'s `GameOverLevel` are near-identical screens (title text, a "Press Any Key To Continue" prompt driven by `StartMenuScript`, and a `continueCallback` supplied by `XLodeRunnerGame`). `level-map-constants.ts` holds the short `Tile` aliases (`Brk`, `Str`, `Lav`, …) every level's map literal is built from.
  - **`TileElement`** (`tile-map/tile-map-types.ts`) is `Tile | TileWithOptions` — a map-literal cell is either a bare `Tile` enum value or a `{ type: Tile; options: T }` wrapper (`TileWithOptions<T extends IBaseTileElementOptions>`) carrying per-cell configuration a plain enum value can't. `XLodeRunnerLevel.setupTileMap()` unwraps it when writing to `TileMap` (`TileMap.setTile`/`getTile` only ever see the bare `Tile`) but also forwards the whole `TileElement` to `createTileGameObject`, which re-unwraps it and reads `.options` when building that tile's scripts. `x-lode-runner-level-1.ts` builds these wrapper cells as named constants near the top of the file (e.g. `SGT: TileWithOptions<IGoldenGateLockOptions>`, `SSG: TileWithOptions<IBeamSwitchOptions>`) rather than inline in the map literal, to keep the map's one-row-per-line formatting intact.
  - **A beam switch and a `GoldenGateLock` are linked by name, not by position.** `OnOffScript.create(gameObject, initialState, name)` registers itself with the single `OnOffManager` GameObject (added once per level by `XLodeRunnerLevel.setup()`) under that `name` when it starts; `GoldenGateLock.create(gameObject, { linkedOnOffScriptName })` looks up that same name through the `OnOffManager` (both throw if the manager, or the named `OnOffScript`, isn't found — these are level-authoring mistakes, not runtime conditions to degrade gracefully from) and copies its `on` state onto the gate's tile every `update()` (`Tile.Empty` when on, back to `Tile.GoldenGates` when off). Multiple gates can share one switch's name (`x-lode-runner-level-1.ts` does this for its two `SGT` cells against one `SSG`/`BEAM_SWITCH_1_NAME`). This replaced an earlier, since-removed version of `GoldenGateLock` that located its switch by a hardcoded map position instead — the name-based lookup is what lets `TileWithOptions` express the link declaratively in the map literal rather than as a magic coordinate in code. `BeamSwitchScript` (`scripts/beam-switch/`, renamed from `SwitchScript`) is the thing that actually flips an `OnOffScript`'s `on` state, based on whether a beam of the matching color is currently landing on its tile.
  - `StartMenuScript` (`src/app/game-x-loade-runner/scripts/start/start-menu-script.ts`) calls its `continueCallback` once any key is pressed (`keyboard.pressedThisRoundCodes.length > 0`). It must be attached to only *one* of a screen's `GameObject`s (currently the "Any Key" prompt, not the "Title", on both `StartMenuLevel` and `GameOverLevel`) — `GameObject.update()` doesn't check `isDestroyed`, so if two objects both carried it, one keypress would fire the callback from both before either's `startLevel()` call resolved, spawning two independent copies of the real level. This is the same failure shape as the tile-interaction one below, just between two menu objects instead of two tile scripts.
  - **The full play loop is wired up through `XLodeRunnerGame`** (`x-lode-runner-game.ts`): `start()` always begins at `StartMenuLevel`; its `continueCallback` starts the real level; dying (see `PlayerScript` below) calls `LivesScript.loseLife()`, whose deferred callback decrements `XLodeRunnerGame.lives` and either restarts the *same* `ILevel` instance (calling `initialize()` again safely rebuilds everything, since the mutable per-playthrough state lives in fresh `GameObject`s, not on the `ILevel`) or, once lives are exhausted, moves to `GameOverLevel`; its own `continueCallback` resets `lives` to `MAX_LIVES` and returns to `StartMenuLevel`, closing the loop.
  - `LivesScript.create(gameObject, lives, loseLifeCallback)` — `lives`/`count` is a fixed snapshot set once at construction and never decremented internally; `XLodeRunnerGame` is the single source of truth for the actual life count, constructing a fresh `LivesScript` with the current count on every level (re)start. `loseLife()` doesn't touch `count` at all — it just calls `engineState.registerAfterUpdate(() => loseLifeCallback())`.
  - `PlayerScript` (`src/app/game-x-loade-runner/scripts/player-script.ts`) owns the death *sequence* (start the death jingle, count down `DYING_DURATION_SECONDS`, then call `LivesScript.loseLife()`) by watching `StateScript.isDying()` — this used to live in `StateScript` itself, but `StateScript` is shared with `Enemy`, so player-only concerns (lives, game over) don't belong there. `StateScript` only tracks the boolean (via the public `die()`/`isDying()`/`clearState()`) and stays in `PlayerState.Dying` indefinitely once set; it no longer times anything or respawns on its own. `resolveState()` triggers `die()` for a dangerous tile *or* a solid wall — the latter covers a trapped character left standing inside a `BlastedBrick` cell that then reforms into a `Brick` around it. `PlayerScript.checkEnemy()` also calls `die()` whenever an `EnemyScript`-bearing `GameObject` shares the player's tile (`TileMap.getObjectsAt`) — touching an enemy kills the player.
  - `EnemyScript` dies the same way (lava or a reformed wall; touching the player never kills an enemy — contact damage is one-directional) but **doesn't** go through `LivesScript`/level-restart: its own `beginDying()`/`DelayedAction` plays `DEATH_ENEMY_JINGLE` (on music channel `'EnemyDeath'` — kept distinct from `PlayerScript`'s `'Death'` channel deliberately, since `MusicPlayer.register`/`play` key playback state by that name string, so reusing one would let a near-simultaneous player and enemy death cut each other's jingle off) and then `respawn()`s: teleport back to the `reSpawnPosition` passed into `EnemyScript.create(gameObject, reSpawnPosition)`, `stateScript.clearState()`, and a fresh `DelayedAction` re-enters `Borning`.
  - **Every character also spends its first `BORNING_DURATION_SECONDS` frozen in `PlayerState.Borning`** (a spawn-gate animation, `ON_PLAYER_BORN`), both to visualize spawning and to stop a just-respawned character (or its chaser) from acting before the player can react. A freshly constructed `StateScript.state` is `null`, and `resolveState()` treats `null` the same as `PlayerState.Borning` — frozen, ignoring input/pathfinding, until something calls the public `StateScript.startLife()`. `PlayerScript` and `EnemyScript` each own their own `DelayedAction` (see below) that calls `startLife()` once its delay elapses; `StateScript` itself never starts or clears the freeze on its own.
    - `startLife()` does **not** set `state` directly — it only flips a private `isBorn` flag, which `resolveState()` consumes (clearing it) the first time it runs afterwards, letting execution fall through to the normal state computation below instead of hard-returning `Stand`. This matters because `this.state` itself is only ever written by `setState()`, which short-circuits (skipping the `BitmapSpriteRenderer.setAnimation()` call) whenever the newly-resolved state equals the one already stored. If `startLife()` set `state = Stand` directly (the original implementation), and a character happened to be already grounded with nothing forcing movement — so `resolveState()`'s real computation also lands on `Stand` — `setState()` would see `Stand === Stand`, skip, and leave the sprite pinned on `ON_PLAYER_BORN`'s last frame forever, even though the character was logically alive and would even respond to later input/pathfinding that led to a genuinely different state. With the `isBorn` flag, `this.state` stays `Borning` right up until `setState()` runs with the real resolved state, so the "did it change" check always sees a real transition on that first post-Borning frame — regardless of what that resolved state turns out to be. `clearState()` (re-entering Borning, e.g. on `EnemyScript.respawn()`) also resets `isBorn`, so a stale not-yet-consumed wake-up from an earlier life can't skip the fresh freeze.
    - This was the root cause of a reported bug where a character would flash its spawn animation once and then just sit there, looking dead/invisible, forever — it happened specifically when a character spawned already grounded (no `Fall` step needed before settling into `Stand`), which is also why `EnemyScript`'s own chase failing to find a path (see the `x-lode-runner-level-1.ts` map note below) made it so visible: with no path, `resolveState()` keeps resolving to `Stand` every frame, so the sprite had no other trigger to ever refresh off the Born frame.
    - `x-lode-runner-level-1.ts`'s map must keep every `PlS`/`EnS` spawn cell on a side of the level that's actually connected (by floor, stairs, or crossbar) to the rest of the playable area — `EnemyScript.findNextStep()`'s BFS simply gives up and leaves the enemy standing still forever if no path exists, which looks identical to the Borning bug above from a player's perspective (character never does anything). The level's `BrickHard` block spanning columns 11–14 on the floor row (plus column 11 one row above it) cuts the map into two disconnected halves with no other vertical route (stairs only exist at column 9) between them; both spawn cells need to land on the same side of that wall.
  - **`DelayedAction`** (`src/app/engine/delayed-action.ts`) is the shared timer both `PlayerScript`'s `borning`/`dying` and `EnemyScript`'s `borning` are built on: `advance(deltaTime)` accumulates elapsed time and calls its `action` once past `durationSeconds`, then *latches* — every later `advance()` call is a no-op, so calling it more times than expected (or not destroying the owning `GameObject` in time) can't fire `action` a second time. Extracted specifically to stop this "elapsed timer, then trigger a callback" shape from being copy-pasted per script, and to remove the need for each caller to `null`-out its own timer field after firing.
- **`x-lode-runner-constants.ts`** (`src/app/game-x-loade-runner/x-lode-runner-constants.ts`) holds small cross-script game constants (currently just `MAX_LIVES`) — put a constant here, not on the class most closely associated with it (e.g. not on `LivesScript`), when multiple otherwise-unrelated scripts need to import it, to avoid tying their imports to each other's module. Don't anchor unrelated layout math to it either — `GoldScript`'s HUD position used to derive from `MAX_LIVES` and silently drew off-screen once `MAX_LIVES` dropped below 3; it's now a fixed offset from `SCREEN_WIDTH` instead.
- **`GameObject`** (`src/app/engine/game-object/game-object.ts`) is a Unity-style entity: an `IEngineState` reference, a `position` (`Vector2`), and a list of `Script` instances. Constructed via `GameObject.create(engineState, position, scriptFactories)`, where each `scriptFactory` is `(gameObject: GameObject) => Script` — factories (not script instances) are passed in so each script can receive a reference to the `GameObject` that owns it. `start()`/`update()`/`destroy()` just fan out to every attached script's same-named lifecycle method.
- **`Script`** (`src/app/engine/game-object/script.ts`) is a base class with no-op `start()`/`update()`/`destroy()` methods, meant to be subclassed (Unity `MonoBehaviour`-style). `IScript` (`i-script.ts`) exists alongside it but is currently an empty marker interface that `Script` doesn't implement — not yet wired up to anything.
- **`BitmapRenderer`** (`src/app/engine/scripts/bitmap-renderer.ts`) is a `Script` that copies a single static `number[][]` bitmap onto `ScreenBuffer` at its `GameObject`'s position every `update()`.
- **`BitmapSpriteRenderer`** (`src/app/engine/scripts/bitmap-sprite-renderer.ts`) is a `Script` that cycles through an array of bitmap frames: each `update()` advances `spriteIndexTime` by `framesPerSecond * deltaTime` and draws `bitmap[Math.floor(spriteIndexTime)]`.
- **`Vector2`** (`src/app/engine/math/vector-2.ts`) implements `IVector2` (`{ x: number; y: number }`) and is constructed via `Vector2.create(x, y)`.

### Screen buffer and rendering

- **`ScreenBuffer`** (`src/app/engine/screen/screen-buffer.ts`) is a plain class — construct it via the static `ScreenBuffer.create()`. It just holds a private `number[][]` pixel buffer, exposes it read-only via a `buffer` getter, and `copy(source, x, y)` to blit sprite data into it (delegating to `ScreenHelper.copy`, which mutates in place). It has no knowledge of canvases or rendering.
- **`ScreenHelper`** (`src/app/engine/screen/screen.helper.ts`) is a static-method helper class (this repo's convention: group pure/stateless logic in `*Helper` classes rather than free functions) with `unpackRgba`, `defaultPixels` (blank transparent buffer), and `copy` (the mutating blit primitive).
- **`screen.constants.ts`** (same folder) defines `SCREEN_WIDTH`/`SCREEN_HEIGHT` and single-letter packed-pixel constants — `_` (transparent), `W`/`R`/`G`/`B` (white/red/green/blue) — deliberately short so literal sprite arrays read as a recognizable pixel-art grid in source.
- **`ITextureEffect`/`TextureEffect`** (`src/app/engine/scripts/effects/i-texture-effect.ts`) is a pluggable per-glyph transform: `apply(texture: number[][], x: number, y: number): number[][]`, run only `if (effect.isEnabled)`. `TextHelper.print()` (`src/app/engine/screen/text.helper.ts`) chains a glyph through each effect in order before drawing it, passing that *glyph's own* absolute screen position (not the string's starting position) as `x`/`y` — an effect that varies its output by position (e.g. staggering a shimmer per character) needs this to tell one glyph in a string from another. `DissolveTextureEffect` ignores `x`/`y` (a fade doesn't need position); `ColorOverrideTextureEffect` (`color-override-texture-effect.ts`) forwards them into its per-pixel callback, offset by each pixel's place within the glyph, so the callback receives real screen coordinates.
- **`Screen`** (`src/app/ui/components/screen/screen.ts`) is the only place canvas-drawing code lives. It sizes itself from `window.innerWidth` (via a `(window:resize)` host binding), computes `scale = windowWidth / SCREEN_WIDTH`, and emits that via a `scaleChange` output. In `afterNextRender()` it registers its own `render(buffer)` method with `Engine.instance.setRender(...)` — every Engine tick calls back into `Screen` with the latest buffer, and `Screen` does the `ImageData`/`putImageData` work to paint it.
- **`Header`** (`src/app/ui/components/header/`) just displays the current scale (`{{ scale().toFixed(2) }}x`) — no controls.
- **`App`** (`src/app/app.ts`) is the composition root: it holds the `scale` signal (fed by `Screen`'s `scaleChange`, displayed by `Header`) and kicks off everything by calling `Engine.instance.start(XLodeRunnerGame.create())` in `ngOnInit()`.

`src/app/data/glyphs.ts` / `sprites.ts` hold hand-authored `number[][]` pixel art (e.g. `LETTER_A`; `MAN_STANDING_FRAME_1..4`; `OBJECT_EMPTY`/`OBJECT_BRICK`/`OBJECT_STAIRS`), each built directly from `screen.constants.ts`'s pixel constants (no parsing/decoding step).

### Player-triggered tile interactions (game-x-loade-runner)

A tile `Script` that reacts to the player "using" it (e.g. `MirrorScript.rotate()`) should expose a public method for the action, not poll the keyboard itself in `update()`. `BuilderScript` (`src/app/game-x-loade-runner/scripts/builder-script.ts`) is the single place that reads the build/interact keys and knows which cell the player is facing; it looks up the `GameObject`(s) at that cell, finds the relevant script, and calls its action method directly. Letting multiple scripts each listen for the same key independently causes them to double-fire on one keypress (this previously needed a `Keyboard.stopPressedThisFramePropagation()` workaround to suppress one listener in favor of another — removed once the interaction was centralized in `BuilderScript`).

### Known issues (found while reviewing the GameObject/Script addition)

- **`BitmapSpriteRenderer`'s frame-wrap logic looks wrong.** When `spriteIndexTime >= bitmap.length`, it resets via `spriteIndexTime - Math.floor(spriteIndexTime)`, which is just the fractional part of the number (equivalent to `% 1`), not `% bitmap.length`. For any animation with more than one frame this snaps the animation back to indexes 0–1 instead of looping through all frames.
- **`onMoseMove` is a typo for `onMouseMove`**, but it's the real, consistently-used method name across `IGame`, `XLodeRunnerGame`, and `Screen`'s call site — don't "fix" it in just one place.

### Testing notes

jsdom does not implement a real canvas 2D context — `canvas.getContext('2d')` logs "not implemented" and returns `null`. When testing canvas-drawing code (currently in `Screen`), stub `getContext` with a minimal fake context object that records what gets passed to `putImageData`, so tests assert on real rendered pixel output.

### Browser verification

A Playwright MCP server is configured (`.mcp.json`) specifically because canvas rendering can't be verified through jsdom-based unit tests — use it to visually confirm rendering/resizing behavior in a real browser when changing anything under `src/app/ui/components/screen/` or `src/app/engine/`.
